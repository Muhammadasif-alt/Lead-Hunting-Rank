# Technical Specification #7 — Queue + Worker Architecture (LOCKED)

## 1. Core Principle
API heavy work khud execute nahin karegi. User/Event/Scheduler→NestJS API→PostgreSQL→Transactional Outbox→BullMQ→Redis→Workers→Domain/AI/Providers. Rule: API accepts work; Workers execute work; PostgreSQL remains source of truth.

## 2. Redis Not Source of Truth
Redis queues/delayed jobs/locks/rate limits/temp cache/worker coordination. Business truth: campaign status/conversation/company/meeting/opportunity/external action/approval/suppression — PostgreSQL. Redis lost → business history not lost.

## 3. Queue Groups
system/events; discovery/resolution/research/enrichment/verification/website-audit; signals/scoring; ai/conversation; campaign/email; calendar/meetings; memory/knowledge; analytics/experiments; notifications/maintenance. Not every tiny operation separate queue.

## 4. Priority Classes
P0 CRITICAL (unsubscribe processing, emergency controls, inbound high-value reply, critical provider reconciliation). P1 HIGH (inbound conversation, meeting request, pricing reply, approval continuation). P2 NORMAL (campaign send, follow-up, research for active opportunity). P3 BACKGROUND (Market Exhaust, bulk enrichment, analytics rebuild, memory revalidation).

## 5-6. Active Relationships Beat Cold Research + Starvation Protection
Market Exhaust 18,000 research jobs queued; prospect "send me your calendar" must jump priority. Reserved capacity: conversation/inbound, external actions, critical system work. Remaining: research/discovery/analytics/maintenance. Prevent permanent starvation.

## 7-8. Job Envelope + Minimal Payload
JobEnvelope: jobId/jobType/workspaceId/correlationId/entityType/entityId/priority/attempt/maxAttempts/idempotencyKey/createdAt/scheduledFor/payload. Minimal payload: companyId/taskId/correlationId — NOT entire company object/300 messages/KB. Worker reloads current authoritative data from DB; queued payload can be stale.

## 9-10. Explicit Job Types + Command≠Job
DISCOVERY_RUN_QUERY/RESOLVE_COMPANY/RESEARCH_COMPANY/ENRICH_COMPANY/VERIFY_CONTACT/AUDIT_WEBSITE/PROCESS_INBOUND_MESSAGE/CLASSIFY_REPLY/GENERATE_REPLY/PREPARE_CAMPAIGN_STEP/PREPARE_EMAIL/EXECUTE_EMAIL_ACTION/CHECK_AVAILABILITY/BOOK_MEETING/EXTRACT_MEMORY/REVALIDATE_MEMORY/PROCESS_OUTBOX/RECONCILE_PROVIDER — strong typing. StartCampaign domain command → CampaignStarted event → PREPARE_CAMPAIGN_ENROLLMENTS job. Job is not business command replacement.

## 11-14. Transactional Outbox + States + Publisher Crash
Problem: DB transaction succeeds but Redis queue write fails. Correct: BEGIN TRANSACTION → update Campaign → insert CampaignStarted event → insert OutboxRecord → COMMIT. Outbox Publisher: OutboxRecord→BullMQ→mark published. Outbox crash may republish → consumers must be idempotent. Outbox alone doesn't provide exactly-once.

## 15-17. At-Least-Once + Inbox Receipt + Idempotency Layers
Design around job/event/webhook may execute more than once. Exactly-once delivery NOT assumed. At-least-once + idempotent processing = safe effective behavior. InboxReceipt: consumer/event_id/processed_at — already processed? YES→ACK, NO→process. Idempotency layers: event/job/domain-command/external-action/provider where supported.

## 18-20. Email Safety Problem + ExternalAction + Identity
Worst bug: worker sends email → crashes → BullMQ retries → same email again. Campaign NEVER directly gmail.send(); prepare message→policy→ExternalAction created→Email execution job. ExternalAction durable DB entity with id/type/workspace_id/entity_type/entity_id/provider_account_id/payload_snapshot/payload_hash/idempotency_key/status/attempt_count/provider_reference/created_at/executed_at.

## 21-24. Idempotency Key + Prepare vs Execute + Revalidation + Atomic Claim
Logical email key: campaign:{campaignId}:enrollment:{enrollmentId}:step:{stepId}:message:{messageId}; UNIQUE(idempotency_key) in DB. PREPARE_EMAIL: generate/ground/check contact/run policy/create ExternalAction. EXECUTE_EMAIL_ACTION: actual provider side effect. Immediately before Gmail send revalidate: workspace outbound active?/campaign active?/enrollment active?/conversation replied?/suppression clear?/human takeover?/approval valid?/message unchanged?/send window valid?/mailbox healthy?/frequency cap? → else DO NOT SEND. Claim: UPDATE external_actions SET status='EXECUTING' WHERE id=? AND status='QUEUED' → rows affected 1=own, 0=someone else/already handled.

## 25-29. Hard Email Crash + Ambiguous Result + States + Reconciliation + Provider Native Idempotency
Gmail accepted email → network response lost → worker doesn't know → UNKNOWN outcome exists; do not immediately resend. Worker check UNKNOWN_OUTCOME → reconcile provider state using provider IDs/metadata where possible → found sent→SUCCEEDED, confirmed not sent→safe retry, cannot determine→HUMAN/controlled recovery. ExternalActionExecution states: PREPARED/WAITING_APPROVAL/APPROVED/QUEUED/EXECUTING/SUCCEEDED/WAITING/BLOCKED/FAILED/CANCELLED/UNKNOWN_OUTCOME. Use provider-native idempotency keys/request IDs where supported, but architecture must remain safe where provider lacks perfect idempotency.

## 30. Message State vs External Action
Message represents conversation/business communication. ExternalAction represents execution attempt/control. Keep separate; one message may have execution metadata without mixing entire provider workflow into message status.

## 31-34. Scheduled Follow-Ups + Durable Scheduler + FU Flow + Reply Before FU
Redis alone can't be durable business schedule; DB stores CampaignStepExecution due_at/status. Periodic scheduler queries due_at<=now + status=SCHEDULED + no active execution → ensures BullMQ job exists. Postgres schedule truth; BullMQ execution mechanism. FU flow: step 1 sent→determine next eligible time→DB next_step_due_at→delayed BullMQ job→wake up→reload current state→re-evaluate. Prospect replies before FU: Conversation Reply→Enrollment REPLIED→cancel known delayed jobs where possible; even if cancellation fails, tomorrow worker checks Enrollment REPLIED and exits without sending. Double protection.

## 35-43. Retry Strategy + Categories + Transient + Rate Limit + Auth + Validation + Policy + AI + Structured Retry + Retry Budget
Categories: TRANSIENT/RATE_LIMIT/AUTH/VALIDATION/POLICY/NOT_FOUND/UNKNOWN/PERMANENT. TRANSIENT (502/temporary DB/provider 503)→exponential backoff+jitter (30 sec/2min/10min/30min provider-specific). Rate Limit 429→Retry-After or provider backoff; may pause affected provider bucket. Auth (OAuth expired)→AUTH_REQUIRED→integration state update→affected jobs BLOCK/WAIT→Human Attention; don't retry 50x. Validation (invalid email format)→retry won't fix→FAILED/BLOCKED. Policy=BLOCK is not worker failure; job completes operationally while business action BLOCKED/CANCELLED; don't send to technical DLQ. AI schema invalid/timeout/unavailable → retry same model/fallback allowed/human escalation depending task/risk. Structured AI retry: model invalid schema→Attempt 1→validation failure→repair/retry; strict max attempts, not recursive forever. Every job defines max_attempts + max_elapsed_time; after limit FAILED or DLQ.

## 44-47. DLQ + States + Manual Retry + Replay vs Retry
Logical DLQ persisted in PostgreSQL DeadLetterRecord: job_type/entity/original_job_id/attempts/failure_code/last_error/payload_reference/first_failed_at/last_failed_at/resolution_status. DLQ states OPEN/RETRY_SCHEDULED/RESOLVED/IGNORED; Screen #18 shows. Manual retry first revalidates current state: old job "Send campaign email" but prospect unsubscribed → BLOCK, not send. Retry same logical operation; replay reprocesses historical event — tight permission, default safe/internal mode unless explicitly designed.

## 48-54. Concurrency + Provider vs Worker Limits + Rate Limiters + Layers + Mailbox Throttling + Backpressure
Concurrency configured per job family; conceptual profile: Inbound Conversation HIGH reserved, Email Execution controlled, Calendar controlled, Research medium/high, Discovery medium, Enrichment provider-limited, Website Audit CPU/network-limited, Analytics background, Maintenance background; no hard numbers before VPS/provider benchmarks. Provider concurrency ≠ worker concurrency: 20 research workers but 5 req/sec provider → provider limiter enforces 5/sec. Provider limiter key by provider/credential-account/endpoint-capability (gmail:mailbox123:send ≠ gmail:mailbox123:read). Additionally workspace policy limits: workspace outbound/day, campaign/day, mailbox/day, contact/week, company/week. Most restrictive applicable wins. Mailbox throttling: normal 100/day, degraded health 40/day, critical 0/day. Backpressure: if queue too large, conversation work continues while slowing market discovery/bulk research/experiments/analytics rebuild.

## 55-59. Worker Pools + Worker App + Explicit Processors + Handler Pattern + Distributed Locks
Initially same codebase logical pools: critical-worker/outbound-worker/conversation-worker/intelligence-worker/bulk-worker/maintenance-worker; fewer actual processes day one, split later. /apps/worker imports database/shared/events/policy/providers/ai, not frontend. Explicit processors: process-outbox/discovery/research/enrichment/inbound-message/email-action/calendar-action/memory — avoid one 5000-line worker file. Handler: validate envelope→load current entity→check idempotency/state→execute domain op→persist result→emit event/outbox; external adds policy revalidation→atomic claim→provider→reconcile result. Locks only where needed: one Market Exhaust planner per mission, one conversation reply planner per conversation, one provider sync per account. Lock is not durable business truth.

## 60-65. Lock Expiry + DB Concurrency + Optimistic + Conversation Concurrency + Debounce + Critical Exceptions
Every distributed lock TTL; long jobs heartbeat/lock extension to avoid permanent lock. For critical transitions prefer DB mechanisms: transactions/conditional updates/unique constraints/optimistic concurrency over Redis locks. Mutable aggregates carry version; worker loads version 12, another action makes 13 → CONFLICT → reload/re-evaluate. Two inbound emails quickly → per-conversation sequencing/order (conversation:{id}). Conversation debounce: prospect sends "Hi"/"Can you send pricing?"/"Also available Friday?" rapidly → short configurable debounce window processes coherent batch where appropriate. But unsubscribe "Stop emailing me" → processed immediately; no debounce for suppression.

## 66-72. Inbound Webhook Architecture + Raw Provider Event + Duplicate Webhook + Polling Fallback + Gmail Inbound + Outbound Email + Meeting Booking
Gmail/Provider→Webhook/Poll→API ingestion→validate provider→persist raw provider event→dedupe→Outbox/Event→HIGH-priority inbound job. Webhook endpoint does minimal work synchronously. ProviderEvent: provider/account_id/provider_event_id/type/received_at/payload_reference+hash/processing_status; unique provider+account+provider_event_id. Providers can resend webhook; unique prevents duplicate logical processing. Where webhook unreliable/unavailable: periodic sync checks provider cursor/history; system tolerates webhook+poll discovering same message; idempotency handles duplicate. Gmail inbound flow: Gmail→Provider Event→Normalize Message→message.received→cancel cold FUs→Conversation HIGH→intent/memory/qualification→policy→Reply/Ask/Wait/Block. Outbound flow: Campaign Step Due→Prepare Campaign Step→load current account state→generate grounded message→validators→policy→ExternalAction→Email Queue→execution-time policy→atomic claim→Provider Send→Provider result→MessageSent→schedule next step. Meeting: meeting intent→Scheduling Agent→Availability query→prospect selects slot→BOOK_MEETING ExternalAction→execution-time availability check→Calendar Provider→provider event ID→Meeting BOOKED. If slot disappeared → WAIT/new slot selection, never fake booking.

## 73-79. Discovery Queue + Market Exhaust Iterations + Budget Check + Entity Resolution + Research Dedupe + Fan-out + Partial Completion
Discovery Mission→Planner Job→Query Jobs→Raw Observations→Resolution Jobs→Canonical Companies→Coverage Assessment. Don't queue 10,000 future queries blindly; rounds: Round N→execute bounded query batch→resolve results→measure marginal yield→Coverage Agent→Plan next round. Before each new round: mission still active?/budget remaining?/provider healthy?/saturation reached?/human pause? → stop/wait/block/complete. Entity resolution pipeline: normalize→candidate lookup→deterministic match→high-confidence merge→ambiguous candidates→AI/Human review if worthwhile; never parallel-merge same companies without concurrency protection. Research jobs dedupe by company+research purpose+freshness window; same running → reuse/wait rather than paying twice. Research fan-out: website fetch/contact discovery/enrichment/tech detection/review collection; parent tracks children; don't rely solely on BullMQ parent status for business state, persist mission/task status in DB. Partial Research Completion: website✓ owner✓ email verification provider down → parent PARTIAL, not retry everything.

## 80-84. AI Queue + Priority + Model Rate Limits + Cost Reservation + Enrichment Reservation
AI work carries agentType/taskType/entity/contextRequest/riskClass/modelClass/budget; worker calls central AI Gateway. Priority: P1 active conversation reply / P2 campaign personalization / P3 market analysis+historical summarization. AI Gateway manages requests/min/tokens/min/concurrency/provider availability/budget; queue layer responds WAIT/backoff instead of uncontrolled failures. AI cost reservation for expensive tasks: estimate cost→reserve mission budget→execute→settle actual cost; prevents 50 parallel jobs each seeing same remaining budget and collectively overspending. Same pattern for paid enrichment in Market Exhaust with parallel workers.

## 85-92. Scheduled Jobs + Business vs System Schedule + Cron Idempotency + Job Cancellation + Bulk Cancellation + Pause Semantics + Kill Switch
Recurring: outbox publishing/provider reconciliation/integration health/mailbox health/signal refresh/memory revalidation/knowledge freshness/campaign due-step reconciliation/meeting reminders/analytics aggregation/backup verification metadata/cleanup — BullMQ repeatable jobs or scheduler service. Business schedule: "Follow up John Friday" = business data in PostgreSQL. System schedule: "Run reconciliation every 5 minutes" = scheduler configuration. Don't mix. Cron jobs should be idempotent: two scheduler instances trigger same maintenance task → only one logical execution via lock/idempotency. Job can become obsolete: campaign paused/conversation replied/meeting cancelled/goal cancelled → try removing known BullMQ jobs; correctness must not depend on successful removal; worker always checks current state. Bulk cancellation: don't synchronously delete 100k jobs in user request; mark business scope paused/cancelled immediately + cleanup queue asynchronously; workers revalidate so no unsafe actions execute. Pause campaign: DB campaign=PAUSED immediate source of truth; queue may still contain jobs; workers see Campaign PAUSED→no action. Global Kill Switch: Workspace outbound=EMERGENCY_STOP immediate at execution gate; we do not need to successfully remove every Redis job first.

## 93-99. Worker Heartbeat + Health + Queue Health Metrics + Lag Alert + Stalled Jobs + Side-Effect-Free vs External Retry + Poison Jobs
Each worker process records heartbeat: worker_id/worker_type/started_at/last_heartbeat_at/version; Redis live heartbeat + operational history where useful. Screen #18: Conversation Worker✓/Outbound Worker✓/Research Worker✓/Maintenance Worker✓ + queue depth/oldest waiting job/failure rate/processing latency. Per queue metrics: waiting/active/delayed/completed/failed + oldest_wait_age/jobs per min/avg duration/p95 duration/retry rate. Queue Lag Alert more useful than queue length: 10,000 background jobs may be fine; inbound conversation oldest wait = 8 minutes is serious; alert based on workload class SLA. BullMQ stalled detection + domain architecture checks: worker dies mid-research→retry safely; dies mid-external side effect→reconcile before retry. Side-Effect-Free Retry: calculate score/generate summary/parse website generally retry safe. External Send email/Book meeting needs stronger handling. Poison jobs: same job repeatedly crashes due bad payload → max attempts→DLQ, no infinite retry storm.

## 100-104. Circuit Breaker + Scope + Provider Health Event + Failure Isolation + Redis/Postgres/AI Failure + Graceful Shutdown
Circuit Breaker per provider/capability: CLOSED→failures→OPEN→cooldown→HALF_OPEN→test→CLOSED; on open new affected work→WAIT instead of thousands of doomed requests. Scope: "Gmail mailbox A send" broken while "Gmail mailbox B send" works; avoid disabling entire system. Changes emit ProviderDegraded/ProviderUnavailable/ProviderRecovered; AI Sales Manager reacts. Failure isolation: lead provider down→existing conversations work; LLM down→CRM+deterministic ops work; calendar down→email may work but AI cannot claim meetings booked; analytics worker fails→sales execution continues. Redis failure: API can serve safe read operations but background execution degrades; no pretending actions were queued if they weren't; outbox remains in PostgreSQL and publishes after Redis recovery. Postgres failure: external autonomous actions should fail closed; worker won't send email using stale Redis-only data when can't revalidate DB state. AI provider failure: conversation requiring AI→WAIT/HUMAN depending urgency; don't generate canned unsafe answer pretending success. Graceful shutdown on deploy: stop accepting new jobs→finish/abort safe work→release resources→shutdown; long-running tasks persist checkpoints where worthwhile.

## 105-109. Deployment Compatibility + Job Payload Versioning + Event Versioning + Correlation/Causation + Example Trace
Worker versions overlap during deployment → important evolving payloads need schemaVersion; workers reject/handle unsupported safely. Job payload versioning: jobType=PROCESS_INBOUND_MESSAGE + schemaVersion=2; don't silently interpret old payload with incompatible new assumptions. Event versioning similarly event_type+schema_version; new version only for incompatible contract changes. Correlation ID: one user goal → Goal/Mission/Discovery/Research/Campaign/Email/Reply/Meeting → corr_abc123 propagates through jobs/events. Causation ID: Event B caused by Event A.

## 110-113. Logs + Email Content Logging + Provider Error Sanitization + Worker Security + Queue Naming/Environment
Structured logs: job_id/job_type/workspace_id/entity/correlation_id/attempt/duration/result/error_code; never log secrets. Don't dump full email bodies into infra logs; business message already in controlled database; logs use IDs+metadata. Provider errors may contain email addresses/tokens/request details; sanitize before operational logging. Workers get only required secrets; research worker doesn't need Gmail send credentials if deployment separation allows; initially same worker app may share environment but provider gateway + app permissions enforce boundaries; later narrower secrets per process. Queue naming includes environment: production:conversation/production:email/staging:conversation so staging never consumes production jobs.

## 114-118. Environment Isolation + Dry-Run + Replay Sandbox + Queue Dashboard + Human-Friendly Failure
Production: separate DB/Redis/provider credentials. Staging: separate DB/Redis/test-provider sandbox credentials. No shared queues. Campaign test mode: generate/validate/policy evaluate/create preview but external action executor disabled/mock. Replay sandbox: historical inbound messages replayed against new Conversation Agent in evaluation mode; no external actions allowed; useful for AI regression testing. Queue Dashboard in Screen #18 System Health/Queues/Failed Jobs/DLQ/Provider Incidents/Worker Health; Command Center only business-impacting issues. Never just "BullMQ Job 1832 failed"; AI Sales Manager says "Gmail authentication expired. 14 outbound actions are safely blocked; no messages were lost. Reconnect the mailbox to continue." Technical detail remains in Admin.

## 119-124. Market Exhaust Queue Example + Campaign Queue Example + Mailbox Fairness + Contact Lock + Account Protection
Austin landscapers: Create Market Mission→Planner→Query Batch #1→5 provider/search jobs→raw results→Resolution→unique companies→coverage assessment→Query Batch #2→...→marginal yield low→Mission COMPLETED; never millions of uncontrolled jobs. Campaign with 1,000 prospects: don't queue all 1,000 emails same second; Campaign Scheduler→eligible sends→mailbox capacity→time window→controlled jobs. Multiple campaigns share mailbox A/B/C → allocate capacity by priority/campaign policy/mailbox capacity/fairness. Contact-level lock outbound:{contactId} optional short coordination; DB/account-conflict policy remains authoritative. Account-level protection potentially stronger company outbound coordination to avoid two campaigns simultaneously emailing two people from same small business against policy.

## 125-129. Meeting Reminders + Nurture + Long-Term Scheduling + Analytics Jobs + Projection Rebuild + Memory Jobs + Critical vs Enrichment Intelligence + Notification Queue
Meeting reminders: store schedule in DB; worker wakes→meeting still BOOKED?/reminder relevant?/recipient allowed?→execute; cancelled meeting→no reminder. Nurture: never queue BullMQ job six months and trust blindly; store next_contact_at in PostgreSQL; periodic scheduler activates due nurture items. Short delay: BullMQ delayed job + DB record. Long delay: DB first + scheduler materializes jobs near execution; keeps Redis manageable. Analytics jobs: business events trigger lightweight projection updates; heavy analytics batch/background; no reason to slow inbound email because revenue report rebuilding. Projection rebuild: source events/domain records exist → projection can be rebuilt without altering operational source records. Memory jobs: inbound conversation save message first, then async memory extraction/qualification extraction/summary update; conversation doesn't disappear if memory worker fails. Some reply decisions need synchronous-enough AI processing; secondary relationship graph update/long-term memory compression/analytics can happen later. Notification queue: notification failure → separate retry; should not roll back OpportunityWon; domain truth remains committed.

## 130-134. Exactly-Once Business Outcome + Email Safety Formula + Queue Recovery Formula + Initial VPS Layout + Scaling Order
Don't promise exactly-once delivery infrastructure; engineer unique logical action+atomic state transitions+idempotent consumers+execution revalidation+provider reconciliation to produce effectively once business outcomes. Email safety: Logical Message→unique idempotency key→ExternalAction DB record→policy authorization→queue→execution revalidation→atomic claim→provider request→provider reference→persist success. If ambiguous: UNKNOWN_OUTCOME→RECONCILE, not blind resend. Queue recovery: Postgres business state+Outbox+durable schedules+reconciliation → Redis/BullMQ can be rebuilt; exactly why Redis cannot be source of truth. Initial VPS: Docker Compose web/api/worker/postgres/redis/reverse-proxy; not 15 physical worker containers day one; one worker app can process multiple queues; later worker-conversation/outbound-intelligence/bulk independently replicated without redesign. Scaling order: increase worker concurrency carefully→add worker replicas→move Postgres/Redis to stronger hosts→only if justified extract specialized services; no premature microservices.

## 135. Queue Architecture Golden Rules — LOCKED
1 PostgreSQL is business truth. 2 Redis/BullMQ is execution infrastructure. 3 API does not perform long-running work. 4 DB+event consistency uses Transactional Outbox. 5 At-least-once delivery assumed. 6 Every important consumer idempotent. 7 External actions have durable DB identities. 8 External actions revalidate immediately before execution. 9 Ambiguous provider outcomes reconciled, not blindly retried. 10 Business schedules live in PostgreSQL. 11 BullMQ jobs can always become stale. 12 Worker must load current state before acting. 13 Inbound/live sales work outranks cold bulk work. 14 Provider and business rate limits separate. 15 Failures classified before retrying. 16 DLQ for unrecoverable technical jobs. 17 Pause/Kill Switch works even with already queued jobs. 18 Queue cleanup not relied upon for safety. 19 Correlation + causation IDs follow workflows. 20 Worker scaling happens before microservice extraction.
