# Technical Specification #12 — Deployment Architecture (LOCKED)

## 1. Deployment Philosophy
Initial target: Single Production VPS + Docker Compose + Containerized Apps + Off-host Backups/Object Storage. No Kubernetes initially. Web↔Reverse Proxy↔NestJS API↔PostgreSQL/Redis/BullMQ; workers behind provider gateway.

## 2. No Kubernetes Initially
V1: Kubernetes✗ Service Mesh✗ Kafka✗ Multi-region✗ Microservices✗. 4–5 users internal platform ke liye operational complexity zyada, actual benefit kam. Start Docker Compose; scale jab actual metrics justify karein.

## 3-7. Production Services + Docker Images + Roles
Initial Compose stack: reverse-proxy/web/api/worker/postgres/redis. Potential supporting services: backup/monitoring/object-storage adapter depending hosting. Multi-stage Docker builds: Dependencies/Build stage→Production Runtime Stage; final image only runtime needs; smaller images/fewer attack surfaces/faster deployment. Run as Non-Root where practical. Container health checks: web health/api liveness/api readiness/worker heartbeat/postgres health/redis health.

## 8. PostgreSQL Container Caveat + Redis + Persistent Storage
Containerized PostgreSQL acceptable for initial VPS if storage/backups correctly configured; later migration path to Managed PostgreSQL without changing business architecture. Redis not source of truth. Never rely on container writable layer for PostgreSQL/Important uploaded files/Critical operational data; containers must be replaceable. Object storage uses StorageProvider abstraction for KB documents/attachments/website snapshots where required/meeting files/exports/large provider artifacts. Could initially use S3-compatible remote service; architecture shouldn't bind business code to one vendor; interface putObject()/getObject()/deleteObject()/getSignedUrl().

## 9-12. Domain Structure + HTTPS + Internal Networking + Public Ports
Fixed recommended initial: app.domain.com with reverse proxy: /→Next.js; /api/*→NestJS; /webhooks/*→API direct route. Simplifies cookies/CORS/auth/deployment. Production: HTTP→redirect HTTPS; TLS managed automatically where possible; no production authenticated traffic over plain HTTP. Internal services: api→postgres, api→redis, worker→postgres, worker→redis over private network; Postgres/Redis no public Internet ports. Public ports: ideally only 80/443 + restricted admin access; keep 5432 Postgres and 6379 Redis not public.

## 13-15. Environment Separation + Test Provider + Outbound Default
Recommended: Development/Staging/Production. Development: local machine Next.js/NestJS/Worker/Postgres/Redis via Docker Compose where useful; providers use Fake adapters/Sandbox/Test accounts. Staging: same architecture, separate DB/Redis/secrets/integrations; never production DB clone with unnecessary live sensitive data unless specifically sanitized/controlled. Production: only reviewed builds, production secrets/DB/provider accounts/outbound controls. Absolute rule: Development code must not accidentally send through production Gmail. Environment-specific credentials and provider restrictions enforce. Fresh deployment should start OUTBOUND_PAUSED, not immediately ACTIVE; authorized human/system readiness flow activates after checks. FakeEmailProvider/FakeCalendarProvider/FakeLeadProvider for dev/testing; fake email saved locally, no external email.

## 16-17. Repository + Branching
One Git repository revenue-os/ with monorepo packages/apps. Simple workflow: main/feature/*/fix/*; main deployable; no complicated GitFlow. Pull Request Gate before production merge: lint/typecheck/unit tests/critical integration tests/build/migration validation.

## 18-21. CI + Production CD + Immutable Images + Tags + Shared Build + Docker Images + Multi-Stage
CI pipeline: Push/PR→Install locked dependencies→Lint→Typecheck→Tests→Build→Security/dependency checks→Container build. Production CD: Build immutable images→Tag release→Push registry→Server pulls release→Pre-deploy checks→Migration→Start/update services→Health checks→Release complete. Never SSH server/nano source file/restart Node for normal production deploy; deploy versioned artifact/image. Don't depend only on latest; use revenue-os-api:<commit-sha> or release version for deterministic rollback. Monorepo pipeline understands package deps; database/shared/policy/providers/events build before dependent apps. Separate production images for web/api/worker even though one monorepo. Multi-stage Docker: Build stage vs Production Runtime Stage; final image only runtime needs; smaller attack surface/faster deployment.

## 22-26. Health Checks + Startup Dependencies + Database Migration + Migration Container + Failure + Expand/Contract
Each service exposes health; api liveness/readiness; don't assume container started=dependency ready; API/workers retry/wait sensibly for DB startup. Important order: Backup/check→Run migration job→Verify migration→Deploy compatible application; exact order can differ for expand/contract. Migration explicit: pnpm prisma migrate deploy through controlled deployment step; not every API replica independently racing migrations. If migration fails: do not continue normal deployment; keep previous version where safely possible; investigate. Expand/Contract: Release A add new schema + old/new code compatible; Release B backfill/use new schema; Release C remove old schema — reduces downtime/risk.

## 27-30. Worker Deployment + Version Compatibility + Job Versioning + Safe Side Effects
Workers deployment: Mark old worker draining→Stop accepting new jobs→Finish/release active jobs→Stop old worker→Start new worker. Jobs shouldn't contain arbitrary serialized code assumptions; payload IDs/Task intent/Schema version; worker loads current canonical state. Long-lived jobs jobType+jobVersion; new worker can handle old version/upcast/safely reject or requeue. Deployment during outbound: persistent ExternalAction/Idempotency/Atomic claims protect across worker restart. Webhook availability during deploy matters: provider retries + inbound deduplication add protection.

## 31-34. Minimal Downtime V1 + Blue/Green Later + Rolling API + SSE Consideration
4–5 users don't need complex zero-downtime orchestration immediately; target minimal controlled downtime with strong data/external-action safety. Correctness > fake zero downtime. If needed later: Blue/Green reverse proxy switch after health check, but DB compatibility still careful. Multiple API replicas eventually → rolling update behind proxy/load balancer; not required initially. SSE connections reconnect during deploy; frontend automatically reconnects + refreshes current read model.

## 35-37. Scheduler + Responsibilities + Scheduled Jobs Are Reconsideration
Need only one logical scheduler execution for certain jobs; avoid same maintenance scheduled 3x. Use dedicated scheduler worker or distributed scheduling lock/idempotent scheduling. Scheduler responsibilities: signal refresh/memory revalidation/knowledge freshness/analytics aggregation/backup checks/provider health/nurture eligibility/scheduled campaign reconsideration. Scheduled time reached→Queue evaluation→Reload current state→Policy→Action; not automatic blind send.

## 38-41. Database Backup Architecture + Frequency + Retention + Verification + Restore Drill + Failure + Monitoring + Secrets Backup
Minimum: Production PostgreSQL→Automated backup→Encrypted backup→Off-host destination. Final exact frequency depends on agreed RPO. Architecture supports frequent DB backups/daily retained backups/longer periodic retention. Configurable generations: Recent/Daily/Weekly/Monthly depending storage/business requirements. Backup job success ≠ backup proven; automated checks: file/object exists/expected size/checksum where appropriate/encryption valid/upload succeeded. Periodic restore test: create isolated DB→restore latest backup→integrity checks→verify critical entities→record result. Backup failure creates Incident+Human Attention+Admin notification; don't silently fail for weeks. Command Center doesn't need routine backup noise; Settings/System Health shows Last successful backup/Last restore test/Backup destination health. Critical failure alerts humans. Do not simply include plaintext production .env in ordinary DB backup; secrets recovery has separate secure procedure.

## 42-48. Disaster Package + State After Restore + Provider Reconciliation + Calendar Reconciliation + Redis Recovery + Queue Recovery Scanner + Outbox Recovery
Need documentation containing: Infrastructure requirements/DNS setup/Container registry/Environment variable inventory/Backup location/Restore procedure/Secret recovery procedure/Provider reconnect procedure/Post-restore checks. After restore: OUTBOUND_PAUSED until DB integrity✓/Redis✓/Workers✓/Suppression✓/Policy✓/Provider accounts✓/Email reconciliation✓/Calendar reconciliation✓. Important because backup may be older than external provider state: example backup 10:00, email actually sent 10:04, server lost 10:05 → restored DB may not know send succeeded; therefore outbound should not immediately resume; reconcile Gmail/external action state first. Calendar likewise: restored system checks provider calendar before pending booking/reschedule operations. Redis: don't blindly restore stale queue and execute everything; new Redis→reconstruct/requeue required pending work from PostgreSQL through controlled recovery. Database can identify ExternalActions waiting/Missions incomplete/AgentTasks queued or waiting/Scheduled eligibility checks and safely recreate required jobs. Unpublished OutboxEvent rows remain in PostgreSQL; dispatcher resumes after recovery — major reason transactional outbox exists.

## 49-57. Production Monitoring Architecture + Metrics + AI Metrics + Business Safety + Alert Routing + Health Checks + Disk + Logs + Correlation + Production Debugging + Release Metadata/Audit
Initial monitoring covers Host/Containers/Application/Database/Redis/Queues/Providers/Business safety/Backups. Host: CPU/RAM/Disk/Load/Network/Uptime. Container: restarts/CPU/Memory/Health. API: request count/latency/4xx/5xx/active SSE/auth failures/rate limits. DB: connections/slow queries/storage/locks/transaction failures/backup status. Redis/BullMQ: queue depth/oldest job/active/failed/DLQ/retry rate/processing latency. Outbox critical: pending events/oldest unpublished event/dispatcher errors; stuck outbox makes app appear healthy while workflows stop. Provider per integration: success rate/error rate/latency/429s/auth failures/quota/last successful operation. AI: requests/latency/errors/tokens/cost/schema failures/fallbacks/escalations; do not expose hidden reasoning. Business safety: suppression blocks/duplicate prevention/unknown external outcomes/approval invalidations/grounding failures/knowledge conflicts/emergency stops. Alert severity-based: Warning→System Health, Major→Admin notification, Critical→Immediate owner/admin alert; no alert fatigue. Separate liveness/readiness/dependency/provider/business safety health: Gmail outage shouldn't make API process appear dead. Single VPS disk monitoring critical + log rotation/retention/compression + resource limits/request size limits/rate limiting/connection timeouts/queue backpressure.

## 58-65. Agent/Prompt/Policy/Knowledge/Feature Deployment + Safe Mode + Critical Failure Matrix + Health Metrics + Alert Routing + External Uptime + Log Architecture + Correlation + Production Debugging + Release Metadata/Audit
Prompt revision→Evaluation→Approval where needed→Activate; don't manually edit production prompt in server filesystem. Policy: Draft→Simulation→Review→Activate; policy data is operational configuration, not random source-code tweak. Knowledge revisions publish through Knowledge workflow; no server restart. New feature code deployed but disabled via Feature Flag until ready. High-risk deployment: changing email execution/policy/suppression/approval/idempotency/calendar booking → deploy with Outbound pause/Shadow or canary/Extra monitoring as appropriate. Pre-deploy checklist: tests green/migration reviewed/backup healthy/disk capacity/secrets present/provider status/current incidents reviewed. Critical safety regression tests: Unsubscribe→no send; Suppressed company→no send; Human takeover→obsolete AI send cancelled; Pricing beyond authority→no autonomous commitment; No calendar availability→no invented slot; No approved claim→no fabricated case study; Duplicate worker→no duplicate email; Unknown send result→no blind retry; Kill switch→queued send blocked.

## 66-71. Disaster State + Monitoring Architecture + Production Services + Container Images + Minimal Downtime + Scheduler + Minimal Downtime Principle
After restore first recover into OUTBOUND_PAUSED, not full ACTIVE; verify DB/Redis/Workers/Suppression/Policy/Provider accounts/Email reconciliation/Calendar reconciliation before enabling outbound. After incident, several safe states exist: OUTBOUND_PAUSED, SAFE_MODE, LIMITED_AUTONOMY, FULL_APPROVED_AUTONOMY; system should allow explicit transition with audit, not accidental automatic full autonomy after merely starting container. Automation should not become more dangerous merely because a deploy succeeds.

## 72-79. Queue Idempotency During Deploy + SSE Reconnect + Scheduler Single Execution + Scheduler Semantics + Worker Drain + Job Versioning + Storage Durability + VPS Limits
Deployment shouldn't produce duplicate sends because persistent ExternalAction/Idempotency/Atomic claims protect across worker restart. SSE reconnects; frontend automatically reconnects + refreshes current read model. Only one logical scheduler execution for certain jobs; dedicated scheduler worker or distributed scheduling lock/idempotent scheduling; otherwise same daily maintenance might run 3x. Scheduled time reached→Queue evaluation→Reload current state→Policy→Action; not automatic blind send. Workers drain gracefully; don't kill mid-side-effect. Jobs remain small: IDs/Task intent/Schema version; worker loads current canonical state. Object storage durability via S3-compatible remote service; don't rely on container writable layer. VPS not designed to be sole durability boundary: important data/backups/snapshots off-host where practical.

## 80-89. Secrets Deployment + HTTPS + Domain Plan + Four Corners + Chat/WhatsApp Templates Later + Granular Outbound Disablement + Uptime Monitoring
Environment variables with deployment platform/secret storage; don't commit .env. HTTPS via reverse proxy terminates TLS; no production authenticated traffic over plain HTTP. Domain plan: app.domain.com main app, api.domain.com optional or same-origin /api route; webhooks routed securely. Four-corner requirement for production: DB backups, object storage/documents, secrets recovery, restore procedure. Later WhatsApp/chat templates may need provider approval; do not design as unrestricted bulk messaging. Frequent outbound safety concern: connect mailbox is not same as enabling autonomous sends; Gmail connection can be ACTIVE with workspace outbound PAUSED. In outbound failure events, don't allow stale queued sends to continue across resume; every queued action should pass current policy/safety checks again.

## 90-99. Backup Destination + Database Specifics + Staging Database Flexibility + Worker Concurrency + SSE During Deploy + Scheduler DB Protection + Audit/Activity On Failures
Backups must not remain only on same VPS volume because VPS may be compromised/lost. For DB backups, store off-host or separate durable destination where possible. PostgreSQL critical due canonical truth: config/user privileges/backups/migrations must be accessible only to proper services; no public default port. Staging DB can be created fresh or seeded synthetically; it should never require full production customer data unless explicitly necessary and approved. Worker concurrency should be configurable per queue/priority; live sales conversations must not be starved by bulk research or Market Exhaust. In SSE during deployment, clients reconnect; UI must re-fetch current state rather than assuming stream is continuous. Scheduled tasks in DB should note next_run/last_run/status; scheduler dispatch should be idempotent so a restart doesn't double-execute unsafe external actions. Store critical outcomes like "backup ran", "restore drill failed", "integration disconnected", "provider returned 429" where they can be inspected by authorized admins.

## 100-109. Retry Layers + Correlation ID + Provider Rate/Concurrency + Billing Cost Awareness + Mass Sends + Multiple Providers + Cron vs Queue + Human Touches + Production Config + Environment Variable Inventory
External API calls should have clear timeout, retry class, backoff, and failure reporting; not infinite retries. All background jobs should preserve enough metadata to trace a lead, campaign, company, and message through events; correlation ID or event ID should carry forward where practical. Provider concurrency/rate limits must be surfaced as operationally configurable settings. If Lead Hunter will use expensive enrichment calls, production should track usage so a single runaway market scan cannot quietly generate massive cost. Campaign sending should never be a single uncontrolled Redis job dumping thousands of messages; prioritize, chunk, observe, rate-limit, pause. Multiple providers/regions require mapping tables; Gmail message ID, Google Calendar event ID, and lead-provider company ID should never be treated as our primary internal IDs. For deterministic scheduled tasks such as rechecking a stale source or cleanup, a DB-backed schedule or persistent job table is safer than relying only on ephemeral worker memory. Human touches over automated when high ambiguity: a deployment error should pause sends, surface alert, and stop at gate instead of trying to guess safe resume. Do not store production secrets inside repository, image layers, frontend code, logs, prompts, or AI context. Environment inventory should list every required variable name and intended environment; actual values remain secret.

## 110-121. Locked Decisions
Docker Compose initial deployment. Monorepo with apps/web apps/api apps/worker + packages shared. Behavior boundaries held: AI never owns sender account. Webhook handlers fast-turnaround with idempotency/signature checks/background queue. Provider integration implemented through adapters. PostgreSQL canonical; Redis not permanent truth. Queues persistent/reusable but must preserve safety state. Observability on workers, API, and integrations. Clientside navigation calls backend API only. No browser-side provider tokens. Operational docs separated from developer manuals. Rollout gates for L2/L3/L4 autonomy. Kill/pause always immediately effective on external sends. No raw prompts with secrets or provider keys. Logging pii-minimized where possible. API routes mounted under /api/v1 where appropriate + webhooks separate namespace. OpenAI/provider keys server-side only. Prompt versions stored/auditable. Provider adapters own edge differences. Polling is safety net, not replacement for events where webhook supported. Multi-tenant mental model maintained in schema even for one company initially. Upgrade path to separate workers per queue and VPS tiers remains possible.
