# Technical Specification #10 — API Architecture (LOCKED)

## 1. High-Level API Flow
Next.js Web→REST API/SSE→NestJS API→Auth+RBAC→Validation→Domain Service→Policy Engine→PostgreSQL/Outbox→Workers→Provider Gateway. API ka kaam sirf CRUD nahi; business rules enforce karegi. Rule: Frontend kabhi database, Redis, Gmail, Calendar, lead provider ya LLM directly touch nahin karegi. Har business action authenticated API/domain boundary se guzrega.

## 2-3. Style + Versioning
V1 primary: REST+JSON, SSE realtime, Webhooks external inbound. Abhi GraphQL nahi; WebSockets tab tak nahi jab tak true bidirectional realtime prove na ho. Base /api/v1; breaking change→/api/v2; small field addition har time new version nahi.

## 4-5. Resource vs Command + Never Generic PATCH
Resources: GET/POST/PATCH /companies, /opportunities. Commands: POST /campaigns/:id/start|pause; /conversations/:id/takeover; /approvals/:id/approve; /meetings/:id/reschedule. Generic PATCH status="ACTIVE" banned; start requires audience validation/suppression/mailbox health/policy/budget/approval/state transition guards/audit/events.

## 6-12. Authentication + Context + Workspace + Browser Boundary + Server-Side AuthZ + Permission Format + Authority≠Permission
Every protected request resolves who/which workspace/role/permissions/authority → RequestContext: userId/workspaceId/roles/permissions/authorityLimits/requestId/correlationId/ip/security metadata. Domain services user-supplied userId trust nahi karenge. Even single company: workspace_id rahega; client can't send another workspaceId and gain access; server-side membership verify. Browser never receives DB/Redis/provider refresh tokens/LLM keys/encryption master keys/webhook secrets. Frontend hiding Delete Integration button is not security; direct API call → 403. Permission examples: company.read/update; campaign.read/create/launch; conversation.takeover; opportunity.update; approval.decide; integration.manage; policy.manage; system.kill_switch. Authority ≠ Permission: user may have proposal.approve but max discount=10%; 15% discount→403/authority exceeded or higher approver required.

## 13-17. Response/Error + Status + Business Failure≠500
Single: {data,meta{requestId}}. Collection: {data,page,meta}. Standard error: {error{code,message,details,requestId}}. Machine-readable codes: VALIDATION_ERROR/UNAUTHENTICATED/FORBIDDEN/AUTHORITY_EXCEEDED/RESOURCE_NOT_FOUND/VERSION_CONFLICT/INVALID_STATE_TRANSITION/SUPPRESSED/POLICY_BLOCKED/APPROVAL_REQUIRED/PROVIDER_UNAVAILABLE/PROVIDER_AUTH_REQUIRED/RATE_LIMITED/BUDGET_EXCEEDED/KNOWLEDGE_CONFLICT/STALE_CONTEXT/IDEMPOTENCY_CONFLICT. HTTP statuses: 200/201/202/204/400/401/403/404/409/422/429/500/503. Business failure≠500: prospect unsubscribed + send → 422 SUPPRESSED, not 500.

## 18-27. Validation + Unknown Fields + Serialization + Pagination + Limits + Filtering + Search
Every DTO/schema validated: required/types/enum/length/format/allowed values/nested. Security-sensitive commands: unknown fields→reject, no mass-assignment. DB model≠public API model; explicit response DTOs; Prisma internals never auto-serialize. Cursor-based pagination preferred for high-change datasets: GET /companies?limit=50&cursor=... with nextCursor+hasMore. Offset for small/admin datasets where useful. Limit protection default 50, max 200 endpoint-dependent. Filtering: GET /companies?industry=landscaping&city=Austin&websiteStatus=missing; complex filters→SavedView rather than enormous URLs. Sorting explicit whitelist e.g. sort=priorityScore:desc; no arbitrary SQL. Search: global GET /search?q=... or resource-specific GET /companies?search=...; PostgreSQL FTS+pg_trgm+structured filters; semantic retrieval only where relevant.

## 28-37. Company + Lead Hunter + NL Interpret + Preview
Company endpoints: GET/POST /companies; GET/PATCH /companies/:id; GET /companies/:id/people|facts|signals|memories|conversations|opportunities|activity. Research commands: POST /companies/:id/research|revalidate|audit-website → usually 202+operation reference. Operation status GET /operations/:id queued/running/waiting/completed/failed/cancelled+safe progress. Lead Hunter: markets CRUD; discovery-missions CRUD; start/pause/resume/cancel. NL discovery: POST /discovery/interpret input "Find Austin landscapers with no website" → structured preview territory/industry/website/mode — interpretation≠execution. High-cost: POST /discovery-missions/preview → expected providers/limits/cost range/blockers; user confirms if policy requires.

## 38-45. Campaign + Validation + Preview + Conversation + Reply + Generate Reply + Takeover + Resume AI + Opportunity
Campaign: CRUD + validate/preview/start/pause/resume/complete/archive. Campaign Validation no external send returns audience health/missing data/suppressed/mailbox/policy/budget/knowledge issues. Preview sample messages/audience counts/sequence/experiment split/estimated volume. Conversation: GET /conversations + GET /conversations/:id + GET /messages; POST reply/takeover/resume-ai/close/nurture. Reply: server checks permission/conversation state/suppression/contact/mailbox/policy/knowledge/claims before external action. AI reply draft separate: POST /conversations/:id/generate-reply → draft + knowledge used + risk flags + confidence + required approval; generating≠sending. Human takeover AUTO/ASSIST→HUMAN and pending autonomous outbound invalidated/cancelled. Resume AI: does not blindly restart old queued replies; re-evaluate latest conversation/pending promises/suppression/opportunity/policy. Opportunity CRUD; stage transition explicit POST change-stage not generic stageId patch; server validates transition + creates StageHistory/event/audit atomically. Reopen: explicit POST /opportunities/:id/reopen with permission/reason; no silent PATCH status=OPEN.

## 46-52. Proposals + Meetings + Availability + Booking + Approvals
Proposals: POST /opportunities/:id/proposals, GET /proposals/:id, submit-review/approve/send/supersede. Sent version immutable; edit creates new revision/version. Meeting: CRUD/list/get; POST meetings/availability; POST /meetings/book; reschedule/cancel/complete/no-show. Availability request: meetingType/participants/date range/timezone; response current provider-backed; selecting slot triggers final re-check before booking. Booking supports idempotency: POST /meetings/book + Idempotency-Key → prevents double-click duplicate meeting. Approvals: GET/GET:id; POST approve/reject with optional reason; decision endpoint shows current validity; action changed → 409 APPROVAL_INVALIDATED (exact fingerprint approved, not vague future authority). Approval≠execution guarantee: APPROVED later can still be blocked if prospect unsubscribes/kill switch/mailbox fails/context materially changes.

## 53-59. Tasks + Attention + Knowledge + Memory + Signals + Experiments
Tasks: GET/POST/GET:id/PATCH; start/complete/cancel. Attention: GET /attention; acknowledge/resolve/dismiss; AttentionItem≠Task. Knowledge: CRUD; POST /knowledge/:id/revisions/submit-review/approve/archive; publishing current revision explicit. Knowledge search POST /knowledge/search: structured filters + keyword + semantic with server-side permission/authority filtering. Simulator POST /knowledge/simulate input prospect question/context → proposed answer/KB revisions used/conflicts/gaps/policy result; no outbound action. Memory: GET /companies/:id/memories + GET /people/:id/memories; POST /memories/:id/correct|invalidate. Raw unrestricted memory editing avoided; correction creates history/audit. Signals: GET/GET:id; dismiss/validate/watch by authority. Experiments: CRUD + start/pause/stop/analyze.

## 60-66. Integrations + Policy + Simulation + AI Manager Command Pipeline
Integrations: GET/GET:id; connect/test/reconnect/disable/DELETE. Never return credentials. Capabilities API GET /integrations/:id/capabilities shows EMAIL_READ✓ EMAIL_SEND✓ CALENDAR_WRITE✗ without tokens. Policy: GET/GET:id; POST /policies; POST /policies/:id/revisions/simulate/activate; restricted permissions. Simulation before activation runs against representative scenarios; e.g. 134 ACT/22 ASK/5 WAIT/17 BLOCK + examples. AI Sales Manager core POST /ai-manager/command; raw command→intent parser→entity resolution→permission→impact analysis→structured command→preview/execute/ask clarification. Command response types: ANSWER/PREVIEW/CLARIFICATION_REQUIRED/APPROVAL_REQUIRED/ACCEPTED/BLOCKED.

## 67-72. High-Impact vs Low-Risk NL + Goals + Missions + AI Decisions + Explainability
High-impact: "Pause all campaigns" → Intent + affected 8 campaigns + scheduled outbound affected 437 → explicit confirmation/authorized command where required. Low-risk: "Aaj kitne positive replies aaye?" → direct read query if permitted, no unnecessary confirmation. Goals: CRUD + activate/pause/resume/cancel. Missions: list/get + pause/resume/cancel; creation normally through goal/planner/domain workflow rather than arbitrary unrestricted frontend writes. AI Decision API GET /ai-decisions/:id returns agent/action/decision/reason summary/confidence/risk/evidence references/policy result/timestamp — no private chain-of-thought. Explainability: GET /companies/:id/decision-history or generic /entities/:type/:id/activity with filters.

## 73-80. Analytics + Definitions + Command Center + Read Models + N+1 + Writes Domain-Oriented
Analytics: GET /analytics/overview/funnel/campaigns/sources/revenue. Always explicit period from/to; comparisons via compareFrom/compareTo explicit; never silently arbitrary periods. Metric Definitions GET /analytics/metrics/:metricKey/definition → "Qualified Reply Rate ka exact denominator kya hai?". Command Center read model: GET /command-center returns briefing/metrics/attention/AI activity/pipeline summary/hot prospects/meetings/signals/campaign health/system warnings — frontend doesn't make 80 independent requests. Read models derived projections; canonical writes still through domain services. Avoid N+1: Company 360 should not require 1 company request+50 people+100 facts; page-oriented read endpoints like GET /companies/:id/overview. Read endpoints page-optimized; writes remain explicit domain commands.

## 81-88. SSE + Events + Scope + Notification-Not-Truth + Reconnection + WebSockets Later
SSE endpoint: GET /api/v1/events/stream authenticated. Frontend events: attention.created/conversation.updated/message.received/meeting.booked/opportunity.updated/campaign.health_changed/mission.progress/system.health_changed — not every internal domain event broadcast. Server filters by workspace/user permissions/assignments/resource scope; never entire workspace secrets to every user. SSE is notification, not source of truth; if browser misses event, frontend refreshes canonical/read endpoint. Support event IDs where useful; reconnect can resume or fetch latest read model. WebSockets later only if true bidirectional live collaboration/complex presence/high-frequency interactive features needed; not initial requirement.

## 89-95. Idempotency + Optimistic Concurrency + Conflict
Idempotency-Key header on important create/action endpoints: send message/book meeting/launch action/create paid enrichment/bulk action. Store workspace/actor/endpoint-action/key/request_hash/result_reference/expiry. Same key+same request→original result. Same key+different request→409 IDEMPOTENCY_CONFLICT. Mutable aggregates expose version; update request can include If-Match/expectedVersion/body equivalent. User A edits campaign version 7 while User B changes to 8 → A stale update→409 VERSION_CONFLICT; UI asks refresh/reconcile; no silent overwrite. ETags can help caching/concurrency for suitable reads, but business version remains explicit domain concept.

## 96-101. Bulk + Preview/Dry Run + Correlation + Client Correlation
POST /companies/bulk/tag with selected IDs or segmentId/filterSnapshot for huge segments. Giant segment: segmentId+filterSnapshot better than 500,000 IDs in request. Bulk large request returns 202+operationId; workers process chunks. Never accept unlimited giant bulk payload. Bulk cancel: POST /operations/:id/cancel marks remaining cancelled where possible; already completed external actions can't be magically undone. Per-entity eligibility: bulk action doesn't mean every entity succeeds; result 950 eligible/30 suppressed/12 stale/8 permission-policy blocked; each still gets relevant guards. Dry run: high-impact APIs support dryRun=true or dedicated /preview; dry run must never create external side effect. High-impact APIs can support /preview separately. Request correlation: every API request gets request_id+correlation_id; if command triggers background workflow, correlation follows API→Domain Event→Outbox→Job→Provider. Client can provide safe client correlation reference; server controls internal correlation identity/validation.

## 102-105. Audit Context + Required Reason + No Generic Admin Override + Kill Switch + Resume
High-impact request audit: actor/workspace/action/resource/before-after where applicable/reason/request ID/correlation ID/policy/timestamp. Reason Required for override/reopen won opportunity/disable suppression where legally allowed/change pricing policy/kill switch. Never POST /admin/force bypassing everything; overrides narrow/named/permissioned/audited. Kill switch: restricted POST /system/outbound/emergency-stop; response only after durable DB state changed. Resume outbound: POST /system/outbound/resume changes control state; each pending action revalidates before execution, doesn't flush all pending jobs immediately.

## 106-110. Health + Liveness vs Readiness + Admin Health
GET /health/live answers: is API process alive? Should not fail merely because optional provider down. GET /health/ready answers: can instance safely serve required role? May consider Postgres/critical internal dependencies/Redis depending process role. Authenticated GET /system/health returns DB/Redis/Workers/Queues/Providers/Integrations/Outbox lag without secrets.

## 111-117. Rate Limits + Auth/AI/Search + CSRF/CORS/Headers
Rate limit layers: IP/security/user/workspace/endpoint-specific. Login/auth brute-force protection. AI command bar can be expensive: user limits + workspace AI budget + concurrency. Search: global search shouldn't allow accidental rapid expensive semantic queries indefinitely. CSRF: cookie-based auth requires appropriate CSRF defenses on state-changing endpoints, exact mechanism after final auth impl. CORS production restricted to approved origins; no Access-Control-Allow-Origin: * for authenticated admin API. Security headers: CSP/HSTS/X-Content-Type-Options/frame protections/referrer policy; final in Security Spec.

## 118-122. File Upload + Direct Upload + Export + Export Permission + Import
Upload controlled: size/allowed content type/actual file type/authorization/storage destination; filename alone not trusted. Later large files via signed upload URLs; finalization API verifies uploaded object before ingestion. Export: POST /exports → async operation → short-lived authorized download when ready. Export separate permission; view-a-few-records user doesn't automatically get entire DB export. Import POST /imports flow: upload→parse→validate→preview→map→confirm→process async→report. No blind CSV→DB insertion; import preview shows rows valid/duplicates/invalid emails/unknown fields/potential company matches before commit.

## 123-127. Webhooks Separate + Public Booking Links + Token Scope
External provider webhooks not normal user /api/v1: conceptually /webhooks/google/... /webhooks/provider-x/... with provider auth/signature validation. Webhook handler: verify→persist→deduplicate→queue→respond quickly; no long AI processing before response. Public booking links if later prospect-facing appear: separate /public/v1/booking/... surface with strict limited capabilities; do not expose internal meeting APIs publicly. Public token scope: booking/public tokens encode/reference narrowly: meeting type/allowed salesperson or team/expiry/workspace — not full user session authority.

## 128-139. OpenAPI + Business Docs + Client Generation + DTO Layer + Module Ownership + Controller/Application/Domain/Policy/Repository/Transactions
Generate OpenAPI from NestJS DTO/contracts; internal dev docs: endpoint/input/output/errors/permissions/idempotency requirements. Also document important workflows: how to launch campaign/how approval continuation works/how meeting booking works — endpoint list alone does not explain domain semantics. Frontend can generate typed client/types from OpenAPI where practical to reduce type drift. packages/shared can contain stable primitives; never frontend imports Prisma Company model. Architecture: Prisma Model→Domain Entity→API DTO→Frontend; not Prisma→browser. Each NestJS module owns routes: CompanyModule/CampaignModule/ConversationModule/OpportunityModule; avoid giant ApiController. Controller: parse request/authenticate context/validate DTO/call application or domain service/map response — should not contain 500-line sales logic. Application Service coordinates use case StartCampaign/ApproveProposal/TakeOverConversation. Domain Service owns core business invariants: can campaign transition to ACTIVE? Policy Service answers ACT/ASK/WAIT/BLOCK; does not replace domain validity. Repository layer: don't scatter raw Prisma through system; module-owned repositories/services for important aggregates. Transactions: opportunity stage change+StageHistory+DomainEvent+Outbox atomic.

## 140-146. Timeout + AI Streaming + Long AI + Real Progress + Data Freshness + Confidence
HTTP API shouldn't stay open for 5-minute Market Exhaust; long work returns 202. Short reads/commands reasonable server timeout. AI Streaming: user-facing AI Sales Manager conversational answer may stream explanation later, but streaming reasoning text doesn't bypass structured command workflow; actual command execution remains controlled. Never stream hidden reasoning; expose progress/concise rationale/evidence/actions, not private chain-of-thought. Long complex market plan: POST /ai-manager/command→202 operation; SSE reports Understanding goal/Checking providers/Building plan/Ready for review without fabricating progress. Progress must be real: don't show 73% unless meaningful denominator; for Market Exhaust use sources searched/queries completed/current phase/unique businesses found/saturation estimate. External intelligence responses can expose lastCheckedAt/observedAt/verifiedAt/freshnessStatus so UI doesn't imply stale data is live. Exposed confidence must include what it applies to; never generic "AI Confidence:92%" without meaning. Prefer "Owner identity confidence: HIGH" with evidence.

## 147-151. Money + Dates + Local Scheduling + Enums + Null + Redaction + Field-Level Auth
Money: JSON amountMinor + currency, e.g. {"amountMinor":450000,"currency":"USD"}, not price:4500.00 for precision-critical contracts. Dates ISO 8601 UTC like 2026-10-02T18:30:00Z; UI converts to user timezone. For prospect-local scheduling API can accept localDateTime+timezone then normalize; never silently infer ambiguous timezone for high-impact scheduling. API enum values stable: MEETING_BOOKED not UI labels "Meeting Booked 🎉"; frontend handles display/localization. Null vs Unknown clear: null may mean unknown/not set; don't use fake "Unknown" inside typed nullable fields. Redaction: API serializer removes unauthorized fields: sensitive notes/restricted KB/provider configuration/security data. Field-level authorization: researcher can view company research but not restricted pricing margin; context/API enforces.

## 152-160. Auditability + Frontend Rule + Golden Execution Path + External Side-Effect Path + AI Reply Example + Market Exhaust Example + Pricing Request Example + Idempotency Booking + Stale Campaign Edit
Every high-impact request answerable: who requested/when/which API command/what changed/which policy applied/what external action resulted. Frontend allowed display/collect input/request commands/render progress; NOT decide suppression eligibility/approval validity/pricing authority/campaign safety/meeting truth. State-changing business command: HTTP Request→Authentication→Workspace Resolution→Permission→Input Validation→Current State→Domain Guard→Authority→Policy→Transaction→State Mutation→Domain Event+Outbox→HTTP Result. External side-effect: API Command→Domain Proposal→ExternalAction→Queue→Current-State Revalidation→Policy Revalidation→Atomic Claim→Provider Gateway→External Provider→Result→Domain Event. Example Send AI Reply: POST /conversations/123/generate-reply returns draft; human POST /conversations/123/reply; backend permission/current conversation/suppression/grounding/pricing-claim validator/policy → ExternalAction → 202; worker eventually sends. Example Market Exhaust: POST /ai-manager/command "Austin ke maximum landscapers find karo." → parser structured proposed goal → Goal+DiscoveryMission → 202; frontend watches SSE mission.progress and reads canonical GET /discovery-missions/:id. Example Pricing: Prospect asks "Can you do 15% discount?" → Conversation Agent proposes; API/domain checks approved pricing/user+AI authority/discount threshold/opportunity/policy → APPROVAL_REQUIRED; Approval API handles next step; no frontend shortcut. Example Double Click Booking: browser sends two bookings with same Idempotency-Key → first 202 accepted, second same logical result; not second calendar event. Example Stale Campaign Edit: user opened version 14, another edits to 15, first saves 14 → 409 VERSION_CONFLICT; UI refresh/reconcile; no lost update.

## 161-169. Performance Targets + Caching + Deprecation + Internal Compatibility + External Developer API + API Keys + Outbound Webhooks
No guaranteed SLA before real infra testing; targets: normal reads fast interactive/commands fast validation+acceptance/long work async/realtime updates via SSE; heavy AI/provider work never blocks basic CRM browsing. Safe read models may cache, but never cache as authority for Suppression/Pricing authorization/Approval validity/Kill switch/Current meeting availability. API deprecation: document deprecated + provide replacement + measure usage + remove in future major version; don't randomly break frontend. Internal workers prefer domain/application services rather than HTTP calls back into same monolith; no unnecessary Worker→HTTP→own API. External developer API later on Screen #18 controlled with separate credentials/scopes: companies.read/opportunities.read/webhooks.manage; not same as internal user session. API keys: hash at rest/show secret once/support revoke+rotate/scope/expiration configurable/usage logs; never store raw key retrievable in admin UI. Outbound webhooks future: opportunity.won/meeting.booked/company.created; delivery signed/retryable/idempotent event ID/delivery logs. Actual webhook secret generated securely + stored encrypted/hashed appropriately; never expose repeatedly after creation unless explicitly designed.
